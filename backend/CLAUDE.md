# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

FastAPI service (Python ≥3.12, developed on 3.14) that scores batches of photos for quality. All commands run from this `backend/` directory.

## Commands

Windows venv paths:

```powershell
python -m venv .venv; .venv\Scripts\pip install -r requirements-dev.txt
.venv\Scripts\uvicorn app.main:app --reload          # http://localhost:8000/docs
.venv\Scripts\pytest                                  # all tests
.venv\Scripts\pytest tests/test_processing.py::test_failing_analyzer_does_not_affect_others   # single test
.venv\Scripts\ruff check . ; .venv\Scripts\ruff format .
```

## Architecture

The main endpoint is `POST /api/v1/cull-batch` (multipart `files`); `GET /api/v1/settings` and `POST /api/v1/suggest-preset` support tuning and preset suggestions. The service is stateless. Uploads are never written to disk: `app/main.py` raises Starlette's `MultiPartParser.spool_max_size` to `max_file_bytes` so files stay in RAM. Keep it that way.

The layout is deliberately flat. Request flow: `app/api.py` (router and dependencies) → `app/processing.py`. There, `process_batch` is async: it reads and validates each upload, then fans images out to the shared `ThreadPoolExecutor` stored on `app.state.executor`. Next comes `run_pipeline`, which is sync and runs inside a worker thread, then `app/imaging.prepare_image`, then every analyzer. Response models live in `app/schemas.py`.

**Pluggable analyzers** (`app/analyzers/`) are the core extension point. Teammates build features such as exposure detection in parallel this way:
- Each analyzer subclasses `Analyzer` (`analyzers/base.py`), sets a unique `name` (it becomes the key under `analyses` in the response) and implements `analyze(PreparedImage) -> AnalysisResult(flag, score, metrics)`.
- Analyzers are enabled by an explicit list in `analyzers/registry.py`, which is built once at startup into `app.state.analyzers`. A new feature should add a package `analyzers/<name>/` (analyzer, settings, `__init__` export) and one line in the registry. It should not need changes to the schema, pipeline or endpoint.
- Analyzers must be pure and thread-safe, must never decode or resize (use `image.proxy` (BGR) or the cached `image.gray`), and should raise on failure. If several analyzers need another derived view, add it as a `cached_property` on `PreparedImage` in `app/imaging.py`.
- `score` is in [0, 1], where higher is better. Flags are uppercase strings (`BLURRY`, `SHARP`, …).

**Errors are isolated at two levels.** Never let a single item fail the whole request.
- Image level (`processing._process_one`): wrong type, an oversize file or an undecodable image gives `ImageResult(status="error", error=..., analyses={})`.
- Analyzer level (`processing.run_pipeline`): an analyzer that raises gives `AnalysisOut(status="error")` for that analyzer only, while the others still report.
- Request-level HTTP errors are limited to 413 (more than `max_files_per_batch`) and 422 (no files, or `client_ids` length differing from `files`).

**Result identity:** every `ImageResult` carries `index` (upload position, always set) and `client_id` (echo of the optional `client_ids` form field). Match results to files with these, never `filename`, which can repeat. Set them on every return path in `_process_one`, including errors. The frontend keeps the original `File` objects and exports the kept ones itself, so the backend never stores or returns image bytes.

**Settings ownership:** `app/config.py` (`PHOTOSORT_*` env vars) holds only shared settings: proxy width, workers, upload limits, CORS (default `http://localhost:5173`). Feature settings live in the feature's own `BaseSettings` with their own prefix, e.g. `analyzers/blur/settings.py` → `PHOTOSORT_BLUR_THRESHOLD`.

**Blur analyzer:** builds a local sharpness map, not one global number, so intentional background blur (bokeh portraits) isn't flagged. The grayscale proxy (max 1000px wide) is lightly denoised and passed through a Laplacian, then split into a grid (`grid_cols`, default 12). Per tile it computes Laplacian variance (sharpness) and intensity std (contrast). Flat tiles below `min_tile_contrast` are ignored. Tiles at or above `threshold` (80) are sharp, and the largest 8-connected cluster of sharp tiles is the subject. Flags: `SHARP` if ≥ `sharp_area_ratio` (0.40) of the informative tiles are sharp; `SHALLOW_FOCUS` if the subject has ≥ `min_subject_tiles` tiles, holds ≥ `min_subject_cluster_share` (0.5) of all sharp tiles (rejects scattered specks; waived when the cluster has ≥ `confident_subject_tiles` (5) tiles, since smooth skin fragments real subjects), and is ≥ `min_focus_ratio`× (default 20) sharper than the background median and its mean sharpness is ≥ `min_shallow_subject_sharpness` (100); a lone sharp tile (the only one in the frame) also counts as the subject when its ratio is ≥ `min_single_tile_focus_ratio` (40); otherwise `BLURRY`. Between the `SHARP` and `SHALLOW_FOCUS` checks sits an optional **sharp-region rule**: `SHARP` when the subject cluster covers ≥ `min_sharp_region_area` of the informative tiles, its mean sharpness is ≥ `min_sharp_region_sharpness` and it holds ≥ `min_subject_cluster_share` of the sharp tiles. It is off by default (`min_sharp_region_area` = 1.0) and is enabled by the "Sky & smooth areas" slider and the Landscape preset. Why it exists: on 4,319 real landscapes, big smooth areas (sky, calm water, snow, sand) pass the contrast test yet have no detail, so they diluted `sharp_area` and good photos fell to `BLURRY` (30%) or were misread as `SHALLOW_FOCUS`. Ignoring them (`min_tile_contrast` 10) plus the rule (area 0.05, sharpness 130) cut false `BLURRY` to ~17% while still catching ~97% of mild defocus and ~70% of camera shake (81% on defaults). `score = s / (s + threshold)`, where `s` is the subject's mean sharpness, or the median tile sharpness when the flag is `BLURRY`, so `BLURRY` always scores below 0.5. Images too small for the grid or with no informative tiles fall back to the global variance rule. **Re-blur rescue (on by default):** Laplacian variance measures *how much* fine detail a photo has, not *how crisp its edges are*, so clean but low-texture photos (smooth hills, dunes, sky, long-exposure water, heavy JPEG) read as `BLURRY`. Every tile-level `BLURRY` (grid or global path) is therefore re-checked with `reblur_sharpness` (Crete et al. 2007: re-blur with a 9-px box and measure how much neighbour-pixel variation survives; crisp edges lose a lot, blurred ones don't), computed on the raw gray only at real edges (steps ≥ 3 levels that survive a σ1 smoothing, so sensor noise doesn't count). It becomes `SHARP` when `reblur_sharpness` ≥ `min_reblur_sharpness` (0.56; 0 disables; tied to the "Sharpness strictness" slider), unless `edge_coverage` < 0.25 (crisp specks on an edgeless frame) or `noise_level` > 5 (median-based Immerkær estimate, robust to texture; heavy noise fakes crispness). Rescued score = `0.5 + 0.5·(rb − T)/(1 − T)`. Evidence: 133 hand-picked good landscapes went from 100% to 3% `BLURRY`, all 4,319 landscapes from 30% to 2.1%, while copies blurred with sensor noise added were still caught (noisy σ1.5 defocus ~90%, σ2.5 ~100%, 7 px shake ~74%; the tile rule alone caught more shake, ~91%, but rejected ~45% of good photos). Metrics: `reblur_sharpness`, `edge_coverage`, `noise_level`. The blur metrics also include two tuning-independent scene metrics: `top_detail_ratio` (Laplacian variance of the top third ÷ the bottom third) and `top_brightness_gain` (top-third mean luma − bottom third), used to spot open sky. Synthetic test images: `soft_background()`, `bokeh_image()` and `landscape_image()` (smooth sky over detail) in `tests/conftest.py`. Don't use `blurry_image()` as a background: it blurs to near-uniform gray, which counts as flat.

**Face override (blur, off by default, Portrait preset):** in portraits the tile map often picks the wrong subject. Dim, smooth skin reads as soft at the 1000px proxy (face tiles 1–36), while bright out-of-focus bokeh discs read as sharp (60–178), so the brightest bokeh patch became "the subject" and sharp portraits fell to `BLURRY`. When `face_sharpness` > 0 and a face is detected, the face decides instead: Laplacian variance of the (denoised) face box below `face_sharpness` gives `BLURRY`, and at or above it a tile-level `BLURRY` becomes `SHALLOW_FOCUS` (`SHARP`/`SHALLOW_FOCUS` are kept). Score = `fv / (fv + face_sharpness)`, metric `face_sharpness`. It runs after the re-blur rescue, so crisp bokeh edges can't rescue a soft face. Faces narrower than `MIN_FACE_WIDTH` (5% of the frame) are ignored, and photos without a face are judged exactly as before. Faces come from `PreparedImage.faces` (`app/imaging.py`): the YuNet detector (`app/models/face_detection_yunet_2023mar.onnx`, OpenCV model zoo, MIT, ~230 KB; OpenCV 5 no longer ships Haar cascades) runs on a 320px-wide copy of the proxy (~6 ms per photo), one detector per worker thread because `cv2.FaceDetectorYN` isn't thread-safe. It is a lazy `cached_property`, so the detector only runs when the override is on. Calibrated on 67 hand-labeled photos in `Test_photos/bokeh` (`sharp`/`blur`/`portrait_sharp`/`portrait_blur`): sharp faces read 11.8–150, missed-focus faces 1.5–8.8 (one outlier at 12.1). The "Face focus" slider (Off/Lenient 8/On 10/Strict 13) at On cut Portrait errors from 13 to 6: five have no detectable face (camera-shake light trails, faceless or turned-away subjects) and one soft face reads 12.1, just above the cutoff. Tests pre-fill `image.__dict__["faces"]` instead of relying on the model recognising synthetic pixels.

**Exposure analyzers:** `overexposure` (`OVEREXPOSED`/`OK`) and `underexposure` (`UNDEREXPOSED`/`OK`) are separate packages. Both read `PreparedImage.luma_histogram` (256-bin Y of YCrCb, a `cached_property` computed once per image) through the helpers in `analyzers/luma.py`, and both report the metrics `average_brightness`, `highlight_ratio` (luma ≥ 250) and `shadow_ratio` (luma ≤ 5). A flag needs both a bright (or dark) average and a large clipped share (defaults 160/80 and 6%). `score = 1 - min(brightness severity, clipping severity)`, where each severity is 0.5 at its threshold, so flagged photos score below 0.5. The frontend filters by flag on the client. Do not add per-feature endpoints.

**User tuning:** `app/tuning.py` declares which analyzer settings are user-editable (`PARAMS`, with bounds), plus plain-language `SLIDERS` (each slider's `default_level` = shipped defaults; most have 5 levels with the default at 2) and scene `PRESETS`. `GET /api/v1/settings` returns this catalog with live defaults (the single source of truth, so frontend Reset just re-applies them). `POST /cull-batch` accepts an optional `tuning` form field (JSON `{analyzer: {param: value}}`); it is validated (unknown/locked params, bounds, `min_shallow_subject_sharpness >= threshold`, `confident_subject_tiles >= min_subject_tiles`, `min_sharp_region_sharpness >= threshold`; 422 on failure) and applied per request through `Analyzer.with_overrides`, which builds new analyzers and never mutates the shared startup ones. Locked on purpose: shared limits in `config.py`, `MIN_TILE_PX`, `BACKGROUND_FLOOR`, the kernel, connectivity and blur `denoise`. A new analyzer opts in by adding a `PARAMS` entry (and optionally sliders).

**Scene analyzer and EXIF:** `analyzers/scene` is informational (flag always `OK`, score 1.0, not tunable) and exists to feed preset suggestions: `dark_share`, `vivid_light` (bright *and* saturated pixels, e.g. colored stage lights), `soft_texture_share` (tiles with structure but no sharp detail: blurred crowds, panning streaks), plus `exif_*` camera settings when the file has them. `PreparedImage` keeps the raw upload bytes (`raw`) and exposes `exif` (a `cached_property` using Pillow `read_exif`: exposure time, f-number, ISO, focal length, 35mm focal length, subject distance, macro lens; header-only read, never raises, `{}` when absent). Web downloads usually have no camera settings (none of the calibration photos did), so the EXIF rules are convention-based and unverified on real camera files.

**Preset suggestion:** `app/suggest.py` predicts the best preset for a batch. `POST /api/v1/suggest-preset` takes `{photos: [{flags, metrics}]}` (what `cull-batch` returned, up to 1000) and returns a `PresetSuggestion` (`preset_id`, `confidence`, `reasons`, `alternatives`) or `null`. Each photo becomes boolean indicators from pixels (exposure, blur and scene metrics) and EXIF; each `Rule` has a pixel and an EXIF predicate (a photo matches if either holds). Selection is **priority-first** (concert → wildlife → sports → macro → night → high-key → landscape → portrait): the first rule with ≥ 3 photos and ≥ 40% of the batch wins, because concert and sport photos also look like "a subject on a soft background" and would otherwise lose to Portrait. Other rules with ≥ 25% are alternatives. Every preset except default and strict/lenient cull (intent, not scene) is eligible; macro is EXIF-only. Calibrated on the user's folders (Test_photos: landscapes → landscape, Concert → concert, sport → sports, birds → portrait_bokeh; random 20-photo batches were right 87–100% of the time). Pixels can't tell birds from people, so a bird batch without EXIF gets Portrait / bokeh. Blur metrics depend on tuning, so the thresholds assume default settings and the frontend only asks for batches analyzed with defaults. Calibrate thresholds on real folders with `.venv\Scripts\python -m scripts.suggest_report <folder>`.

## Tests

The `tests/` folders mirror `app/`, and per-analyzer tests go in `tests/analyzers/<name>/`. `tests/conftest.py` provides synthetic `sharp_image()`, `blurry_image()`, `soft_background()`, `bokeh_image()` and `encode()` helpers plus a `client` fixture (`TestClient` with the lifespan run). Use these instead of binary fixture files.
